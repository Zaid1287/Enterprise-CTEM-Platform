Executive Summary

Sentinelware is an enterprise-grade, multi-tenant Continuous Threat Exposure Management (CTEM) platform delivered as a SaaS product. It unifies External Attack Surface Management (EASM), Cyber Asset Attack Surface Management (CAASM), Vulnerability Management, Exposure Management, Compliance Management, Risk Prioritization, Shadow IT Discovery, Brand Threat Intelligence, and an AI Security Copilot into a single cohesive product.

🛡️

EASM

External attack surface enumeration — subdomains, ports, technologies, endpoints, secrets.

📦

CAASM

Complete cyber asset inventory with grouping, tagging, risk scoring, and business impact.

🔍

Vulnerability Mgmt

CVE findings enriched with CVSS, EPSS, KEV, and CISA Known Exploited Vulnerabilities.

📋

Compliance

ISO 27001, SOC 2, PCI DSS, HIPAA, CIS Controls — gap analysis, evidence management.

🤖

AI Copilot

GPT-4o-mini powered explanations, remediation guides, and executive summaries.

👁️

Shadow IT

Discovers rogue assets, SaaS apps, OAuth grants outside your registered inventory.

🎯

Brand Threats

Typosquatting detection, phishing domain monitoring, impersonation alerts.

📊

Risk Scoring

Multi-factor risk engine: CVSS + EPSS + KEV + criticality + exposure + business impact.

Deployment Model

The platform is deployed as a multi-tenant SaaS on Replit infrastructure with a PostgreSQL primary database. Each tenant is strictly isolated via JWT-scoped queries and PostgreSQL Row Level Security (RLS). The system supports four user roles: super_admin, admin, manager, and client.

Authentication & Authorization

Auth Flow

📝 POST /api/auth/login (email + password)
↓
🔐 bcrypt.compare() — password verify
↓ optional 2FA check
📧 TOTP / Email OTP (2FA enabled users)
↓
🎫 Issue JWT access token (15 min TTL)
↓
🔄 Issue refresh token (7 days, stored in DB + SHA256 hash)
↓
💾 Client stores access token in sessionStorage
↓
📤 Every API request: Authorization: Bearer <token>
↓
🔑 requireAuth extracts { userId, tenantId, role }

RBAC Model

RoleScopeKey Permissions
super_adminAll tenantsFull platform control, tenant management, queue monitor
adminOwn tenantAll CRUD, user management, platform settings
managerOwn tenantTriage, scan ops, alert rules, reports
clientAssigned assets onlyView findings, compliance, reports (read-heavy)

Token Lifecycle

  • Access token: JWT, 15-min TTL, signed with SESSION_SECRET, stateless
  • Refresh token: random UUID, 7-day TTL, stored as SHA256 hash in sessions table
  • Session revocation: DELETE /auth/sessions/:id removes DB record
  • 2FA: email OTP flow — enable → confirm → required on next login
  • Avatar: multipart upload, stored as base64 in users table
  • Password reset: time-limited token via email link

Multi-Tenant Isolation

  • Every DB query scoped: WHERE tenant_id = req.user.tenantId
  • PostgreSQL RLS policies enforce isolation at DB level
  • Audit log is immutable — DB trigger blocks UPDATE/DELETE
  • super_admin cross-tenant access goes through getPrivilegedTenantIds()

Risk Score Formula

Risk Score = CVSS component
    + EPSS component (probability of exploitation)
    + KEV bonus (+15 if CISA Known Exploited)
    + Criticality bonus (asset criticality tag)
    + Exposure bonus (publicly accessible + open dangerous ports)
    + Business Impact component (1–10 scale, configurable per asset)
→ Final score: 0–100 · Levels: Critical / High / Medium / Low / Info

Background Worker Architecture

beatScheduler.ts

  • Polls every 60 seconds
  • Dispatches due scan schedules (hourly/daily/weekly/monthly)
  • Asset-frequency scans (nextScanAt ≤ NOW)
  • Calls enqueueOrRun() directly (no HTTP)
  • Startup recovery: re-enqueues stuck scans from boot-30s

scanWorker.ts

  • BullMQ when Redis available
  • In-process FIFO queue as fallback
  • MAX_CONCURRENT_SCANS = 5 (env configurable)
  • MAX_PARALLEL_ASSETS = 3
  • Status: pending → running → completed / failed
  • Stuck scan guard: 10 min timeout

alertWorker.ts

  • Processes notification jobs from queue
  • Evaluates alert rules per tenant
  • Dispatches: Email / Slack / Discord / Telegram / Webhook
  • Platform fallback channels (if no tenant rules match)
  • Per-event deduplication

Queue Architecture (BullMQ + Redis optional)

📥 Job arrives (scan trigger / alert event)
↓
📦 Redis available? → BullMQ queue · Else → in-process FIFO
↓
👷 Worker picks up job (concurrency limit enforced)
↓
⚙️ executePipeline() → all 5 phases
↓
✅ finalizeScannedAssets() → risk scores updated
↓
🔔 dispatchNotifications() → alert rules evaluated

Security Architecture

Layer 1 — Transport & Network
mTLS via Replit Proxy HTTPS enforced in production Helmet (11 security headers) CORS restricted to allowed origins
Layer 2 — Rate Limiting & DDoS
Auth endpoints: 20 req / 15min Global API: 200 req / 15min express-rate-limit with trust proxy Circuit breaker (external API calls)
Layer 3 — Authentication
JWT (RS256 / HS256), 15-min TTL bcrypt password hashing TOTP 2FA (email OTP) Refresh token rotation Session revocation
Layer 4 — Authorisation
RBAC (4 roles) requireRole middleware per endpoint tenantId scoped on every query PostgreSQL RLS enforcement AM client-scope isolation
Layer 5 — Data & Integrity
Drizzle ORM (no raw SQL injection risk) Zod input validation on all endpoints Immutable audit log (DB trigger) Secrets in env vars (never in code) Evidence files — access-controlled download
Layer 6 — Content Security
CSP via Helmet (custom config) No eval() / no inline scripts Stripe webhook raw body validation Multipart upload size limits
